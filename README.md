Reproduce two SomeVer problems using upstream WiX 7.0.1's real five-file
version bootstrap. Requires Git, .NET SDK 10, and Python 3.

```sh
git clone https://github.com/computerquip-work/somever-template-repro.git
cd somever-template-repro
python3 reproduce.py
```

The script clones the public WiX `v7.0.1` tag at
`642f1a0f7c857ffa4fc9fa3f9d1433aab895dd29` into `build/wix` and shows:

1. SomeVer 0.1.1 initially generates all five version files correctly.
2. Adding `v7.0.2` leaves those files stale when rebuilding with 0.1.1.
3. Upgrading only SomeVer to 0.1.2 makes generation succeed, but all five
   outputs contain XML from the final template. The intended-output check
   fails because `global.json` contains XML instead of JSON; the script
   exits 1. A subsequent .NET command inside WiX also fails parsing it.

The affected files are `global.json`, `Directory.Packages.props`, and
`build/SomeVerInfo.cs`, `.rc`, and `.props`. Inspect them under `build/wix`.
Logs and the isolated NuGet cache stay under the ignored `build/` directory.

To also demonstrate the fix:

```sh
python3 reproduce.py --fix --work-dir build/wix-fixed
```

This adds only `Outputs="%(VersionTemplate.OutputPath)"` to the downloaded
SomeVer 0.1.2 target in that run's isolated cache. A fresh upstream checkout
under `build/wix-fixed-corrected` generates all five files correctly at
version 7.0.2, and the script exits 0. A fresh checkout is needed because
the corrupted `global.json` blocks MSBuild startup; the broken files stay
available for inspection. The shared NuGet cache is untouched.

WiX 7.0.1 generates a .NET 9 SDK pin; SomeVer 0.1.2 requires .NET 10. The
bootstrap runs from this repository to select the installed .NET 10 SDK
without changing WiX's SDK template. This checks version generation, not
a full WiX build. The script and output checks were generated by AI.
